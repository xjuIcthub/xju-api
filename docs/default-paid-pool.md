# Default 付费池规则与上线说明

本页记录 Default 共享池付费化的产品口径与一次性上线动作。架构和号池路由仍以 [PLAN.md](../PLAN.md) 与 [architecture-and-pool-tech.md](./architecture-and-pool-tech.md) 为准。

## 余额与用量口径

- `users.quota` 是 **Default 共享池余额**。API Key 选择 `default` 分组时，请求按模型价格与 Default 倍率扣除此余额。
- 用户自己的私人号池不检查、不扣减 `users.quota`，仍照常记录请求、日志和 `users.used_quota`。
- `users.used_quota` 是 **全部池累计用量**，包含 Default 与私人号池，因此不能当作“历史付费金额”。
- 不做自动降级或自动切池。使用哪个池仍完全由 API Key 的分组决定。

## 身份展示

身份只由当前 USD 等值余额即时派生，不新增会员状态字段：

| 当前余额 | 展示 |
|---|---|
| `< $50` | 普通名字 |
| `>= $50` | 流光香槟金名字 |
| `>= $100` | 流光金名 + 银皇冠 |
| `>= $1,000` | 流光金名 + 金皇冠 |

余额消耗跌破阈值后，展示会随下一次用户信息刷新立即变化。该身份目前纯视觉，不影响调度、速率、模型权限或排队优先级。

## 免费奖励

- 每日签到固定奖励 `$0.10`，直接进入 Default 余额。
- 每成功邀请一名新用户，邀请人和被邀请人各得 `$5`。
- 邀请人累计成功邀请达到 3 / 5 / 10 人时，分别一次性额外获得 `$10` / `$20` / `$50`。
- 个人推荐码可重复分享；管理员生成的一次性准入邀请码不建立推荐关系，也不发邀请奖励。
- 密码、OAuth 与微信新注册统一执行同一套邀请码门禁；已有 OAuth/微信账号正常登录时不重复要求邀请码。
- 新账号、一次性邀请码消费、OAuth 绑定和邀请奖励在同一个数据库事务中提交；任一步失败都会整体回滚。`invite_rewards` 的唯一受邀人约束同时防止重复回调和并发注册重复发放。
- 3 / 5 / 10 人里程碑只统计本奖励机制产生的 `invite_rewards`，不会被升级前遗留的 `aff_count` 污染，也不会追发历史邀请。

## 管理入口

- 管理员「账号池」下方的「Default 池倍率」只修改 `GroupRatio.default`，不会改变私人池倍率。
- 管理员「用户」页将 Default 余额和全部池累计用量拆列，并在表格上方显示全站 `SUM(used_quota)`。
- 用户「我的号池」下方的「额度充值」提供余额说明、兑换码入口、充值记录、身份门槛和个人邀请链接。
- 当前只开放**兑换码充值**，在线支付总开关继续保持关闭。运营兑换口径固定为 **`¥1 = $100` Default 额度**；用户支付 `¥N` 时，应发放 `$N × 100` 面值的兑换码。
- 兑换码记录本身只保存内部 `quota`，不保存人民币金额或支付流水。按当前 `QuotaPerUnit = 500,000`，`¥1` 对应的 `$100` 兑换码应写入 `50,000,000 quota`。此换算不能通过修改 `QuotaPerUnit`、`USDExchangeRate` 或 Default 池倍率实现，否则会破坏全站余额、历史用量和模型计费口径。

## 一次性余额清零

只在正式上线维护窗口执行一次，不能放进启动 migration。脚本使用宿主机
`python3` 自带的 SQLite 标准库，不要求额外安装 `sqlite3` 命令：

```bash
# 1. 只读检查，不修改
./scripts/reset-default-balances.sh /opt/new-api/data/one-api.db

# 2. 确认目标、用户数和额度总量后再执行
./scripts/reset-default-balances.sh --apply /opt/new-api/data/one-api.db
```

脚本执行前会跑 SQLite 完整性检查，并使用 SQLite backup API 生成带时间戳、权限为 `0600` 的一致性备份；备份再次通过完整性检查后，才会在一个事务中将所有用户（含管理员）的 `quota` 与旧的可转入 `aff_quota` 清零，把旧的注册送额度配置设为 0，明确启用固定 `$0.10` 签到，并把服务端在线支付总开关 `payment_setting.online_payment_enabled` 写为 `false`。旧支付密钥即使仍留在数据库，也不能创建订单或通过历史回调重新加回额度；当前兑换码充值不依赖此在线支付开关。`aff_history`、`used_quota`、Token 用量和日志均保留。

只读检查还会列出仍可兑换的历史兑换码、待完成的充值订单和有效订阅数量。这三类记录可能在清零后再次提供 Default 池资金，但脚本不会擅自作废；只要任一数量非零，`--apply` 默认拒绝继续。运营已经逐项确认并明确接受后续入账风险时，才可额外传入 `--allow-active-funding`。

成功清零会写入 `XjuDefaultBalanceResetAt` 一次性标记并输出备份 SHA-256。数据库已有标记时，后续 `--apply` 会拒绝再次抹除新余额；只有完成事故复核后才能显式使用 `--force`。

首次上线顺序必须是：**停止旧版 new-api → 执行 `--apply` 并确认成功 → 启动带本功能的新版本**。不能先启动新版本，否则旧余额会在清零前短暂获得金名/皇冠，并能继续用于 Default 池。停止写入也能避免清零窗口内发生充值或消费竞态；新版本启动后会刷新进程内 Option 状态并创建 `invite_rewards` 表。

如果新版本启动失败且决定回滚业务与余额，应保持 new-api 停止，先保存失败现场数据库，再用脚本输出的 `.bak` 恢复 `/opt/new-api/data/one-api.db`，之后才启动旧镜像。只回滚镜像而不恢复数据库，会保留已经清零的余额状态。

本仓库只提供代码和脚本；按照两机护栏，实际执行与部署必须在 Codex-tri 上另行进行。
